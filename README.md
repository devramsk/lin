# LineageOS 21 pre-QPR2 Light GSI

Два unsigned образа: `64VN` и `64GN`. Репозиторий **не содержит всё дерево Android**: оно загружается через `repo` в один постоянный рабочий каталог на сборочной машине. В GitHub не коммитятся сотни гигабайт исходников и бинарные образы. Манифест `LOS21-pre-QPR2/android` и отдельные проекты используют движущиеся ветки; фиксируются ревизии двух репозиториев AndyCGYan и записывается `repo manifest -r`. Патчи и `repopick` создают локальные коммиты, поэтому манифест сам по себе не гарантирует воспроизводимость. Для `64GN` требуется MindTheGapps: проверьте лицензии перед распространением.

## Почему очередь не запускает сборку

Показанный запуск [43585075993](https://github.com/devramsk/lin/actions/runs/43585075993) **отменён**, до исполнения шагов он не дошёл. Ожидание означает, что GitHub не назначил доступный runner со всеми метками `self-hosted`, `linux`, `x64`, `lineage-gsi`; возможны отсутствие машины, offline/busy, несовпадение меток или ограничения группы. Само предоставление прав не создаёт вычислительную машину. API списка runners для текущего подключения вернул 403, поэтому наличие/состояние машин здесь не подтверждено. Обычный GitHub-hosted runner не заменяет подходящий сервер: LineageOS рекомендует около 400 ГБ места и 64 ГБ RAM, а стандартные hosted runners значительно меньше; их задача ограничена шестью часами.

## Что должен сделать владелец

1. Подготовить **выделенную изолированную** машину/VM Ubuntu 22.04 x86_64: рекомендуются не менее 64 ГиБ RAM, 400 ГиБ свободного SSD плюс место под результаты, устойчивый интернет, исходящий HTTPS до GitHub, GitLab, Google repo, LineageOS Gerrit и всех зеркал манифеста. GitHub-hosted larger runner с достаточными ресурсами — отдельный платный вариант, требующий соответствующего плана и другой конфигурации workflow.
2. На GitHub открыть репозиторий → **Settings → Actions → Runners → New self-hosted runner** → Linux/x64. Выполнить показанные GitHub команды на подготовленной машине и при регистрации добавить метку `lineage-gsi` (или назначить её в настройках runner). Не копируйте регистрационный токен в чат; он краткоживущий и нужен только машине. Настроить запуск runner как сервиса согласно инструкциям GitHub. Убедиться, что он **Online, Idle**, имеет все четыре метки и доступен этому репозиторию. Для установки пакетов необходим неинтерактивный `sudo -n` для apt; предпочтительнее заранее подготовленная одноразовая VM.
3. **Settings → Secrets and variables → Actions → Variables → New repository variable**: `LINEAGE_BUILD_ROOT` = абсолютный путь на постоянном диске машины, например `/mnt/lineage/build-21`. Каталог должен быть пустым при первом запуске, доступным пользователю runner и не должен быть Git checkout или содержать ценные файлы. Он должен переживать повторные задания и быть одинаковым при повторе. Если runner сменился, нужно подключить именно тот же диск/содержимое; эфемерный диск или GitHub cache не сохраняет состояние Android-сборки. Не запускайте другие проекты на этом пути. Первый запуск требует 400 ГиБ свободного места.
4. В **Actions → LineageOS 21 pre-QPR2 GSI → Run workflow** выбрать ветку с этой версией workflow. Для автоматического запуска агентом доступ GitHub в Arena должен разрешать чтение репозитория и Actions, запись Actions/workflow dispatch и push в текущую ветку; для диагностики списка repository runners отдельно нужно чтение administration. Владелец может изменить разрешения установленного GitHub-приложения через GitHub **Settings → Applications → Installed GitHub Apps** и подтвердить запрос изменения разрешений, либо повторно подключить GitHub в Arena. Не передавайте в чат токены, пароли или регистрационные данные. Для запуска через интерфейс сам пользователь должен иметь соответствующий доступ к Actions. Даже при этих правах runner должен быть запущен отдельно.
5. После завершения проверить статус всех шагов и скачать артефакты `lineage-audit-*` и `lineage-gsi-*`. Квоты хранения и возможная тарификация больших образов зависят от аккаунта; успешная компиляция не гарантирует успешную загрузку артефакта. При отмене/аварии загрузка логов не гарантируется; копия остаётся на диске runner.

**Безопасность:** репозиторий публичный. GitHub предупреждает об опасности self-hosted runners в публичных репозиториях: недоверенный workflow может исполнить произвольный код на машине. Используйте одноразовую изолированную VM, не храните на ней секреты, ограничьте доступ к запуску/изменению workflows, не выполняйте недоверенные PR и защитите постоянный диск. Установка через sudo предоставляет существенные права. Мониторинг не является независимым полным аудитом исходников или гарантией безопасности образов.

## Этапы и восстановление

Для Actions используется `scripts/staged-build-gsi.sh`: `setup`, `prepare` (upstream sync, repopick и патчи), затем независимые `build-64VN`, `build-64GN` и проверка обоих образов. Подготовка использует функции **зафиксированной ревизии upstream**; образы собираются её же скриптом с `treble nosync 64VN` и `treble nosync 64GN`. Это разделение отличается от единого вызова `treble 64VN 64GN`, но использует те же функции подготовки и последовательность сборки; полная эквивалентность ещё не проверена реальной сборкой. Для точного исходного единого вызова остаётся `scripts/build-gsi.sh` (только новый каталог, без возобновления).

Микрозаписи событий формируются во временном файле `/tmp`, копируются и атомарно переименовываются на постоянном диске в `audit/events`, после чего коммитятся в **локальный отдельный Git-репозиторий** `audit/.git`. Коммиты фиксируют состояние этапа и хеш текущего журнала, а не исходники, образы или полную сборку в GitHub. Логи живут в `audit/logs`, ресурсный монитор — в `audit/resources.log`, манифест и хеши образов — в `audit/`. Исходники и промежуточные файлы хранятся только в `BUILD_ROOT/source`; метки этапов не являются снимками диска. `/tmp` не является постоянным хранилищем. Никаких автоматических push в GitHub нет.

Повторный запуск на том же диске пропускает завершённые этапы; команда сборки прерванного target может быть повторена с `make installclean` upstream. Если файл соответствующего образа уже создан до записи контрольной точки, скрипт останавливается для ручной проверки, а не перезаписывает его. При сбое/прерывании `setup`, `prepare` или `validate` автоматический повтор запрещён: upstream использует `git clean -fdx`, `git reset --hard`, `git am` и `repopick`, а частично применённые изменения нельзя безопасно распознать автоматически. Изучите журнал и используйте **новый пустой BUILD_ROOT**, не удаляя данные автоматически. Контрольные точки предполагают, что владелец не менял дерево, патчи, образы и метки между запусками. Не восстанавливайте состояние копированием только Git-коммитов аудита.

Для ручного запуска на машине:

```bash
BUILD_ROOT=/mnt/lineage/build-21 bash scripts/staged-build-gsi.sh
```

`INSTALL_DEPS=0` отключает установку пакетов для заранее подготовленной машины. `MIN_FREE_GIB` меняет только начальную проверку, не реальные требования сборки. По умолчанию HOME изолирован, сертификаты не используются. Два образа находятся в `BUILD_ROOT/home/build-output`. Перед прошивкой пользователь самостоятельно проверяет совместимость и риски устройства.

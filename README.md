# LineageOS 21 pre-QPR2 Light GSI — GitHub-hosted Actions

Цель — unsigned образы `64VN` и `64GN`. Полное Android-дерево скачивается через `repo` в отдельный каталог runner; оно не закоммичено в этот репозиторий. Стандартный `build_unified.sh treble 64VN 64GN` оставлен в `scripts/build-gsi.sh`. В Actions используется экспериментальная поэтапная обвязка `scripts/staged-build-gsi.sh`: она вызывает функции подготовки из зафиксированной версии upstream и затем отдельно `treble nosync 64VN` и `treble nosync 64GN`. Эквивалентность единому вызову реальной сборкой не проверена. `64GN` использует MindTheGapps — проверьте применимые лицензии до распространения.

## Реальные ограничения

- Standard GitHub-hosted Ubuntu — 4 CPU, 16 GB RAM и 14 GB SSD по спецификации GitHub для публичных репозиториев. Этого недостаточно; освобождение стандартной VM не превращает её в 400-гигабайтный сервер. LineageOS рекомендует для 21 около 400 GB свободного места и 64 GB RAM.
- GitHub-hosted **larger runners** доступны организациям/предприятиям Team или Enterprise Cloud. Например, Linux x64 16 CPU имеет 64 GB RAM и 600 GB SSD по спецификации; фактически свободное место проверяется отдельно. Они тарифицируются и для публичных репозиториев. GitHub ограничивает любое hosted задание шестью часами. Даже на larger runner сборка может не успеть; это ещё не проверено.
- `devramsk/lin` сейчас принадлежит личному аккаунту (`owner.type = User`), поэтому доступность organization larger runner для этого репозитория не подтверждена; по опубликованным требованиям личного репозитория недостаточно. Не переносите репозиторий и не подключайте платную инфраструктуру без решения владельца. Self-hosted runner в этом workflow не используется.
- VM hosted runner уничтожается после job. Для продолжения предусмотрены экспериментальные контрольные точки в GitHub Actions Cache, а не хранение в `/tmp`. По умолчанию весь cache репозитория ограничен 10 GB; лимит можно увеличить, но использование сверх включённых 10 GB тарифицируется. Для нескольких полных копий дерева могут понадобиться **сотни гигабайт или более терабайта**, а загрузка/восстановление могут не уложиться в 6 часов. Cache имеет eviction и не является надёжным долговременным архивом. При запросе фактического лимита текущий GitHub API ответил HTTP 402; бюджет/платёжные настройки не проверены.

## Как владельцу предоставить запуск Arena

GitHub Actions не требует передачи ключей в чат. В этой сессии агент уже смог отправить workflow и запустить бесплатный probe через настроенный GitHub-доступ. Если впоследствии доступ отклоняется, проверьте/переподключите GitHub в Arena и разрешите приложению доступ к нужному репозиторию. Для отправки изменений нужны разрешения Contents и Workflows на запись; для запуска/чтения Actions — Actions write/read. Владельцу может потребоваться подтвердить запросы приложения в **GitHub Settings → Applications → Installed GitHub Apps**. Для ручного запуска через интерфейс пользователю нужен write-доступ. Диагностика списка repository runners отдельно требует Administration: read, но **для hosted-сборки этот доступ не обязателен**. Не отправляйте регистрационные данные, пароли или токены агенту.

1. Чтобы использовать `build`, сначала обеспечьте, что репозиторий действительно может использовать настроенный **GitHub-hosted larger runner** организации Team/Enterprise Cloud, с Ubuntu 22.04 x64, достаточным диском и RAM. Настройте runner group, доступ репозитория к группе, billing и spending budget. В **Settings → Secrets and variables → Actions → Variables** задайте `LINEAGE_GSI_RUNNER` равным назначенной GitHub метке larger runner. Выбирайте только GitHub-hosted: workflow проверяет `RUNNER_ENVIRONMENT` и отказывается выполнять сборку на других runners.
2. В **Settings → Actions → General → Cache settings** проверьте лимит, retention и бюджет. Увеличение лимита до нужного размера и хранение нескольких снимков платное; оцените расходы заранее. Публичные кэши могут быть доступны через workflows PR: не храните там секреты. Скрипт создаёт отдельный HOME без сертификатов.
3. Откройте **Actions → LineageOS 21 pre-QPR2 GSI → Run workflow**, выберите ветку с нужной версией workflow. `mode=probe` — бесплатная проверка синтаксиса/защит и характеристик стандартного runner, сборки не выполняет. `mode=build` — запуск на указанном платном larger runner. Пустой `resume_key` начинает сначала. Запуск на ветке возможен, поскольку workflow уже существует на default-ветке.
4. Для возобновления найдите в журнале **успешно сохранённый** ключ вида `lineage-<run_id>-<run_attempt>-prepare`, `...-build-64VN` или `...-build-64GN` и запустите `mode=build` на той же ветке с точным `resume_key`. Частичное совпадение отклоняется; cache может быть недоступен из-за области видимости ветки, eviction, лимитов или оплаты. Не считайте checkpoint сохранённым только по успешной компиляции: проверьте лог cache save. GitHub может выдавать предупреждения при ошибке сохранения. После неудачной проверки начинайте с последнего сохранённого снимка, а не с неуспешного этапа.
5. При успехе скачайте артефакты `lineage-gsi-*` и `lineage-audit-*`; их размер и хранение тоже могут облагаться платой или превышать лимиты. Если job убит по 6-часовому лимиту или отменён, выгрузка журналов и результатов не гарантируется.

## Устройство и ограничения возобновления

В пределах одной VM отдельные шаги: `setup` → `prepare` (sync/repopick/патчи) → `build-64VN` → `build-64GN` → `validate`. После каждого завершённого этапа до validate сохраняется полное рабочее дерево в cache по уникальному ключу; новая VM восстанавливает его по точному ключу. Для предотвращения конфликтов абсолютный путь `BUILD_ROOT` фиксирован, а `RUNNER_TEMP` проверяется. Cache использует tar для сохранения структуры, но перенос полного дерева с Git/LFS, симлинками и компиляторскими output **ещё не испытан на реальном LineageOS дереве**. Хранилище может исчерпаться при создании cache; действия после отмены/таймаута не гарантированы. Поэтапность не гарантирует укладывания в 6 часов: один sync, компиляция или передача cache может занять дольше. Частично выполненный шаг не сохраняется; при восстановлении предыдущего снимка он выполняется заново.

Микрозаписи о ходе сначала создаются в `/tmp`, копируются и атомарно переименовываются в `audit/events`, затем коммитятся в локальный Git `audit/.git`. Пишутся логи этапов, ресурсы, хеши образов и `repo manifest -r`; bundle аудита и логи отправляются как artifact при обычном завершении/ошибке. Это **не коммит всех исходников или образов в GitHub** и не независимый полный аудит безопасности. Ветки манифеста движутся, а patch/repopick создают локальные коммиты — один manifest не гарантирует воспроизводимость. При локальном перезапуске на том же дереве скрипт не повторяет незавершённые `setup`, `prepare`, `validate`: upstream может применять `git clean -fdx`, `git reset --hard`, `git am` и `repopick`. Для hosted восстановления следует брать предыдущий завершённый снимок. Не подменяйте вручную контрольные метки или файлы.
